## 1. Цель

Хост-плагин, который даёт **per-workspace политику маршрута LLM** и убирает зависимость от
глобального дефолта. Сегодня `agent-default-model` в `~/.dsh/settings.yaml` — единственный
механизм «с какой модели стартует сессия», он один на процесс, и любое переключение модели в
композере **любой** сессии его перезаписывает (наблюдавшееся «перетирание»). Плагин делает
политику свойством воркспейса: файл `.dsh/workspace.yaml` в корне воркспейса задаёт маршруты,
плагин применяет их на уровне шва `agent/request`, не трогая settings.

Покрываемые сценарии (пример для репозитория dsh-plugins):
- мастер-сессии этого воркспейса стартуют на `zai/glm-5.3, effort=max`;
- все дочерние агенты (subagent/subagent_fork/workflow/ralph) стартуют на `deepseek-official/deepseek-flash, effort=max`;
- при отказе основного маршрута (квота/лимиты) — однократная деградация на резервный;
- пользователь может переключить модель конкретной сессии в композере — плагин этому не мешает.

## 2. Предпосылки: швы и проверенные факты

### 2.1. `agent/request` — главный шов [проверено живьём + из контракта]

Waterfall-событие из `@deepseek-ai/dsh-agent` (`lib/types/runtime-types.d.ts`):

```ts
'agent/request'(payload: {
  agent: Agent; turn: number; step: number; signal: AbortSignal;
}, next: () => Promise<LlmCallConfig>): Promise<LlmCallConfig>
```

- `await next()` возвращает конфиг, который машина собралась использовать (agent options на
  первом запросе, записанный header afterwards). **Вернуть замену — маршрут переключается.**
- Выполняется после сборки запроса и `step/start`, до коммита промпта; сообщения мутировать не может.
- Диспетчеризация scope-filtered: слушатель на корневом контексте получает **все** агенты процесса.
- `LlmCallConfig = { provider: string, model: string, reasoningEffort?, temperature?, maxTokens?, stop? }`.

**[проверено живьём]** Слушатель, вернувший `{...cfg, provider:'zai', model:'glm-5.3-flash', reasoningEffort:'low'}`,
реально переключил маршрут ребёнка workflow (ребёнок обязан был унаследовать маршрут родителя).
Доказательство — `request/header` в журнале ребёнка (см. §7). Значит шов ловит **всех** агентов,
включая детей workflow — это важно: через конфиг строк `tool-subagent` workflow/ralph детей
закрепить нельзя (`agentOptions` те строки не принимают), а через этот шов — можно.

### 2.2. `agent/session-start` [из контракта]

Emit-событие, `payload: { agent, source }`, где `source` — причина старта (fresh startup,
resume, …). Можно вызывать `agent.inject()` для подмешивания контекста в первый запрос.

### 2.3. `agent/request-error` [из контракта]

Waterfall, `payload: { agent, turn, step, provider, failure: LlmFailure, retryPolicy, signal }`.
Вернуть `{kind:'retry'}` **не** вызывая `next()` — взять восстановление на себя; `next()` —
делегировать стандартной обработке; `undefined` — финализировать ошибку.
`LlmFailure = { message, code, status?, providerRetryAfterMs?, requestId? }`.
Стабильные коды: `AUTH` (401/403), `QUOTA`, `RATE_LIMIT`, `CONTEXT_WINDOW_EXCEEDED`,
`INVALID_REQUEST`, `SERVER`, `HTTP_<status>`, `TRANSPORT`, `ABORTED`, `TIMEOUT`,
`EMPTY_RESPONSE`, `MISSING_CREDENTIAL`, `INVALID_CREDENTIAL`.

**Важно про связку fallback↔request:** повтор после `{kind:'retry'}` снова входит в
`agent/request`. Правило «заменяем только первый запрос» должно иметь исключение для
«взведённого» fallback-флага (см. §3.4), иначе смена маршрута при деградации не произойдёт.

### 2.4. Утилитарные запросы в водопад не попадают

Compaction и session-title идут прямыми `llm.stream` вызовами мимо loop-only `agent/request`
(так прямо сказано в контракте compaction). Спец-обработка не нужна.

### 2.5. Идентификация «мастер vs ребёнок» [проверено живьём, эвристика]

- Сессии верхнего уровня: id вида `session-<uuid>`.
- Сессии дочерних агентов (spawn/fork/workflow): **голый** `<uuid>` без префикса.
- Первичная эвристика: `agent.session?.id?.startsWith('session-')` → мастер, иначе worker.
- При реализации проверить в типах `dsh-session` наличие честного поля (глубина/lineage/
  parent) — если есть, использовать его, эвристику оставить фолбэком.

### 2.6. Журналы сессий — способ верификации [проверено живьём]

- Путь: `~/.dsh/sessions/<slug-воркспейса>/<sessionId>/session.v3.jsonl.zstd`,
  где slug = путь воркспейса с заменой `/` на `-` (пример:
  `--Users-alex-quidditch-projects-dsh-plugins--`).
- Файл сжат zstd; читать `zstdcat`. События — по одному JSON на строку, различитель —
  поле `type` (не `kind`).
- `request/header` → `data.header.config.{provider, model, reasoningEffort, maxTokens}` —
  **авторитетный** факт о маршруте запроса.
- `tool/call` → `data.name`; `user/message` c `source.kind === 'agent-message'` — входящее
  от агента-ребёнка.
- Самоотчёт модели («какая ты модель?») ненадёжен — модели путаются; проверяй только по `request/header`.

### 2.7. Что уже есть per-workspace из коробки (НЕ дублировать)

- Инструкции: `dsh-agent-instructions` грузит цепочку `AGENTS.md`/`CLAUDE.md` от корня
  проекта до cwd сессии. Скилл-роутинг инструкций у пользователя уже реализован его
  собственным `scope-router`. Плагин в это не лезет.
- Credentials: проектный `.env` уже в цепочке разрешения ключей.
- Скиллы per-workspace — вне scope: у реестра скиллов нет воркспейс-слоя (только global +
  preset), городить фильтрацию — борьба с архитектурой. Нативный путь для scope-наборов
  инструментов — пресет на воркспейс.

## 3. Решения и принятые варианты

### 3.1. Формат конфига — `.dsh/workspace.yaml` в корне воркспейса

```yaml
model:
  default:                      # маршрут мастер-сессий этого воркспейса
    provider: zai
    model: glm-5.3
    reasoningEffort: max
  workers:                      # все дочерние агенты (subagent/fork/workflow/ralph)
    provider: deepseek-official
    model: deepseek-flash
    reasoningEffort: max
  fallback:                     # однократная деградация основного маршрута
    - provider: deepseek-official
      model: deepseek-flash
budget:
  maxReasoningEffort: max       # опциональный потолок effort для воркспейса
```

- Файл опционален: нет файла → плагин полностью инертен (все слушатели сквозные).
- Валидация schemastery-схемой (конвенция DSH), парсинг js-yaml. Ошибки — warning в host-лог
  и инертность, **не** падение загрузки плагина.
- Горячая перезагрузка файла (fs.watch + debounce, паттерн `dsh-settings-file`/`dsh-credentials-local`).
- Секретов в файле нет и быть не должно: маршруты ссылаются на провайдеров, ключи живут в
  `~/.dsh/.credentials.yaml`.

### 3.2. Правило применения к мастеру

Заменяем маршрут **только на первом запросе агента** (пара `turn===1 && step===1` + пометка
агента во внутреннем `WeakSet` «уже решено»). Всё, что пользователь переключил в композере
после, проходит насквозь — водопад больше не вмешивается.

- **Resume-сессии не перекрывать:** у сессии, возобновлённой с уже записанным маршрутом,
  залогированный header должен выигрывать у политики (пользователь мог переключить модель
  до закрытия). Использовать `source` из `agent/session-start`; если источник не «fresh» —
  пометить агента «уже решено» без замены.
- **Известное ребро (принять и задокументировать):** выбор модели в композере *пустой*
  сессии до первого сообщения неотличим от « ambient-дефолта» (композер сохраняет выбор в
  глобальный дефолт) и будет перекрыт политикой. Переключение после первого сообщения — свободно.
- **Задание на исследование:** в транскриптах наблюдается маркер `model-selection`
  (context-injection «model-selection A → B»). Проверить, есть ли durable-запись явного
  выбора модели в сессии; если есть — уважать её и не перекрывать. Это закроет ребро.

### 3.3. Правило применения к работникам (workers)

На первом запросе **каждого** дочернего агента (голый uuid, см. §2.5) заменяем маршрут на
`model.workers`. Это осознанно перекрывает и те закрепления, которые пресеты делают через
`agentOptions` (пример: `subagent_browser` в пресете `standard-browser` закреплён на
`deepseek-v4-flash-vision-exp`). Правило: **политика воркспейса абсолютна в своём воркспейсе**;
кому нужна точная настройка детей пресетом — не задают `workers` в этом воркспейсе.
Задокументировать prominently.

### 3.4. Fallback (деградация маршрута)

Слушатель `agent/request-error`:
- Реагирует только на терминальные для маршрута коды: `QUOTA`, `RATE_LIMIT` (после
  исчерпания штатного retryPolicy — т.е. когда `next()` вернул финализацию), `AUTH`/`MISSING_CREDENTIAL`
  **не** деградируют (лечится ключами, не маршрутом).
- Однократность: per-agent флаг «fallback armed», максимум одна подмена на шаг. Циклы запрещены.
- Механика: `{kind:'retry'}` + взвод флага → повторный вход в `agent/request` → слушатель
  видит флаг и возвращает следующий маршрут из `model.fallback` (обходя правило §3.2).
- Если цепочка исчерпана — `next()` (стандартная обработка ошибки).

### 3.5. Budget-потолки

`budget.maxReasoningEffort` — кламп `reasoningEffort` в заменяющем конфиге. Ничего не
повышает, только понижает.

### 3.6. Вне scope (не делать)

- per-workspace скиллы и тулинг-фильтры (нет слоя в реестре);
- per-workspace инструкции (уже нативно через AGENTS.md-цепочку и scope-router);
- запись в `settings.yaml` и любые `saveSelection` — плагин вообще не трогает глобальный дефолт;
- правки shipped-пресетов; плагин — host-plane строка бандла, не пресет.

## 4. Инварианты

1. **Сквозная инертность по умолчанию:** нет конфига / конфиг невалиден / маршрут не
   зарегистрирован → слушатель обязан вернуть `await next()` без изменений. Сломанный
   yaml-файл не имеет права уронить или изменить ни один запрос.
2. **Всегда полный конфиг:** замена — это цельный валидный `LlmCallConfig`; никаких частичных
   объектов. Остальные поля (`temperature`, `maxTokens`, `stop`) переносим из `next()`-конфига.
3. **Один раз за жизнь агента** (кроме взведённого fallback): после первого решения повторные
   запросы того же агента не трогаем.
4. **Пользовательский выбор свят после первого запроса:** переключения в композере посреди
   сессии не оспариваются.
5. **Не мутировать сообщения** (шов и так не позволяет — не обходить).
6. **Валидность маршрута перед заменой:** цель должна быть зарегистрированным адаптером
   (`ctx.llm.listProviders()`) и валидным `reasoningEffort` для модели — иначе warning + pass-through.
   Невалидный effort у цели (`UNSUPPORTED_REASONING_EFFORT` падает до сети) — просто опустить поле effort.
7. **Модальность цели:** если у целевой модели нет image-входа, а у исходной был — замена
   ребенка допустима только с warning в лог (риск: `chrome_screenshot` в истории ребёнка +
   text-only модель = необратимая смерть сессии по `UNSUPPORTED_CONTENT`). Проверять через
   `ctx.llm.resolveModelInfo(provider, model).inputModalities`, где доступно.
8. **Никаких секретов** в конфиге и логах; ключи только через существующий credentials-слой.
9. **Обратимость:** все слушатели/таймеры/вотчеры регистрируются через `ctx.effect`/диспозеры;
   выгрузка плагина не оставляет ни одного перехвата.
10. **Один host-plane инстанс** на процесс; никаких services в root-realm, кроме опционального
    интроспективного `ctx.provide('workspacePolicy', …)` (только сериализуемые данные, без живых объектов).
11. **Не логировать живые объекты** (никакого JSON.stringify по ctx/agent/session — только листовые поля).

## 5. Точки отказа и их обработка

| # | Точка отказа | Последствие | Обработка |
|---|---|---|---|
| 1 | Замена на незарегистрированный провайдер/модель | Каждый запрос сессии падает — хуже, чем без плагина | §4.6: проверка `listProviders()` при загрузке конфига и перед заменой; невалид → warning + pass-through |
| 2 | Невалидный `reasoningEffort` цели | `UNSUPPORTED_REASONING_EFFORT` до сети | опустить effort у цели; unit-тест на матрицу (glm-5.3 не умеет `off`; deepseek: off/low/high/max) |
| 3 | Замена ребенка на text-only при скриншотах в истории | Необратимая `UNSUPPORTED_CONTENT`-смерть ребёнка | §4.7 модальность-гард + warning |
| 4 | Fallback-цикл | Бесконечные ретраи, расход квоты | §3.4: один fallback на шаг, флаг per-agent, цепочка конечна |
| 5 | Перекрытие явного выбора пользователя (пустая сессия) | «Я выбрал модель, а она не применилась» | §3.2: исследование `model-selection` записи; prominently в README |
| 6 | Перекрытие закреплений пресета (`agentOptions`) | `subagent_browser` дети едут не на vision | §3.3: задокументированное абсолютное правило + рекомендация не смешивать |
| 7 | Сломанный/отсутствующий yaml | — | инертность (§4.1), warning с путём и номером строки |
| 8 | Вотчер файла сработал на частичную запись | Конфиг на полсекунды невалиден | debounce (100–300 мс) + «последний хороший» вариант держится до успешного репарса |
| 9 | Рестарт профиля с плагином | Ошибка композиции роняет хост | строка бандла минимальна; проверка `--dump-config`; конфликтов имён нет (сервис один, опциональный) |
| 10 | Resume-сессия | Плагин перекроет сохранённый маршрут | §3.2: не применять на не-fresh `source` |
| 11 | Одновременные N параллельных детей | Гонки внутри слушателя | слушатель синхронен после `await next()`; состояние — Map по agent/session id, без общих мутаций |

## 6. DoD (Definition of Done)

1. Пакет `~/projects/dsh-plugins/dsh-plugin-workspace-policy`: package.json, `src/` (TS) →
   `lib/` (tsdown), `cordis.patch.yml`, README (RU: мотивация, формат конфига, правило
   абсолютности §3.3, ребро из §3.2), vitest-тесты зелёные, typecheck зелёный.
2. Установлен в web-профиль (`dsh plugin --profile web add …`), профиль перезапущен,
   `dsh --profile web --dump-config` выходит 0 и содержит строку плагина.
3. Живой прогон A (default): в воркспейсе `~/projects/dsh-plugins` лежит
   `.dsh/workspace.yaml` с `default: zai/glm-5.3/max`; глобальный `agent-default-model`
   намеренно другой; **новая** сессия через GUI → в её журнале первый `request/header`
   показывает `zai/glm-5.3/max`.
4. Живой прогон B (workers): та же политика, из сессии запускается и `subagent`, и один
   workflow-ребёнок → в журналах **обоих** детей `request/header` = `deepseek-official/deepseek-flash/max`.
5. Живой прогон C (не вмешательство): в той же сессии пользователь переключает модель в
   композере → следующий `request/header` показывает выбор пользователя, плагин молчит.
6. Живой прогон D (инертность): воркспейс без `.dsh/workspace.yaml` (например `~/projects/platform`)
   → поведение сессий побайтово штатное, в логах плагина тишина.
7. Unit: матрица fallback-решений (QUOTA→retry-next, RATE_LIMIT→retry-next, AUTH→delegate,
   пустая цепочка→delegate), first-request-only, кламп budget, невалидные конфиги, guard §4.6.
8. Регрессия: в воркспейсе БЕЗ политики пресет `standard-browser` продолжает закреплять
   `subagent_browser`-детей на `deepseek-v4-flash-vision-exp` (журнал ребёнка).
9. Рестарт профиля после всех прогонов — чисто, без orphan-состояния.

| default с незарегистрированным провайдером | ключ игнорируется с warning, workers работает |
| effort `off` для цели без `off` | effort опущен в замене |
| первый запрос агента | замена default/workers по правилу |
| второй+ запрос того же агента | pass-through |
| resume-source | помечен «решено» без замены |
| budget.maxReasoningEffort=high, цель=max | заменено на high |
| fallback: QUOTA после исчерпания retryPolicy | {kind:'retry'} + armed, следующий request → маршрут #2 |
| fallback: AUTH | delegate (next()) |
| fallback: цепочка исчерпана | delegate |
