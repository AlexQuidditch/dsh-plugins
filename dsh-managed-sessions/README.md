# dsh-managed-sessions

Модельные инструменты, которые позволяют агенту создавать и вести **настоящие управляемые сессии** (managed sessions) в workspace — то же, что делает кнопка «Новая сессия» в веб-интерфейсе.

Плагин не изобретает новый механизм: он вызывает host-сервис `sessionController` (`@deepseek-ai/dsh-api-session-controller`) — тот самый код, который обслуживает GUI. Новый бандл не нужен, ядро не патчится.

## Зачем, если есть `subagent`

| | `subagent` | managed session |
| --- | --- | --- |
| runtime-владение | child родителя (`parentAgent`) | root: `agents.roots()`, никто им не владеет |
| durable-шапка | `parentSession` + `origin: 'subagent'` | обычная сессия с `cwd` (+ workspace) |
| жизненный цикл | дренируется вместе с родителем (`drainContinuableDescendants`) | живёт сам, переживает ход и сессию родителя, резюмится с диска |
| Session API | `sessionController` отклоняет операции (guard на subagent-owner) | полный доступ: `list` / `inspect` / `page` / `follow` / `rename` / `cancel` |
| GUI | не сессия workspace | полноценная сессия в сайдбаре: пользователь открывает, читает, дописывает |

То есть субагент — это «позвать помощника внутрь хода», а managed-сессия — «завести отдельного исполнителя, которого видно и можно продолжить руками».

## Инструменты

| Инструмент | Что делает |
| --- | --- |
| `session_spawn` | Создать новую сессию (с привязкой к workspace, если каталог уже зарегистрирован как workspace) и сразу доставить ей первый промпт. Параметры: `prompt` (обязателен), `cwd`, `title`, `agentPreset`, `provider` / `model` / `reasoningEffort`. Возвращает `sessionId`, фактический маршрут модели и пресет. |
| `session_send` | Доставить сообщение в существующую сессию; холодную поднимает с диска. `mode=queue` (по умолчанию) — в очередь следующего хода, `mode=steer` — в текущий ход. |
| `session_status` | Без аргументов — список сессий с флагами `running` / `blank` / `subagent` и их `cwd`. С `sessionId` — `live agent`, `running`, число событий, чем закончился последний ход и текст последних ответов ассистента (`messages`: 1–10). |
| `session_cancel` | Отменить активный ход сессии, не выбрасывая её очередь. |

`cwd` по умолчанию берётся из сессии вызывающего агента (`exec.agent` → `sessions.get(id).header.cwd`), поэтому «заспавни в моём workspace» работает без аргументов.

## Пресет новой сессии

По умолчанию ребёнок наследует **пресет вызывающей сессии**: сессия, поднятая из `vv-controller`, работает под `vv-controller`, а не под деплоймент-дефолтом. Порядок разрешения:

1. явный `agentPreset` в вызове инструмента — побеждает всегда, и если такого пресета нет, спавн падает **до** создания сессии;
2. пресет родителя: сначала проекция `agentPreset` (она учитывает переключение пресета до первого хода), затем durable-шапка сессии (`header.agentPreset`, пишется при создании);
3. если у родителя пресета нет — деплоймент-дефолт (`settings.yaml` → `agent-presets.default`, иначе `config.default` строки `agent-presets`).

Наследование никогда не роняет спавн: если пресет родителя больше не резолвится (его удалили), сессия создаётся на дефолтном, а в результате приходит `warning`, который виден и в карточке вызова. Отключается через `inheritPreset: false` в конфиге строки.

## Как это устроено

1. `sessionController.create({ workspaceId | cwd, agentPreset? })` → `agents.ensureSession` создаёт обычную сессию; при `workspaceId` дополнительно выполняется `workspace.attachSession` — именно это ставит строку в группу workspace в сайдбаре. Каталог резолвится через `workspaceRegistry.resolveByPath(cwd)`.
2. `sessionController.prompt({ requestId, sessionId, mode, content }, signal)` → резюмирует агента (холодную сессию поднимает с диска) и кладёт сообщение в inbox, после чего root-агент крутит свой ход. `requestId` идемпотентен (тот же id не доставится дважды), поэтому каждая доставка минтит новый.
3. Если у вызывающей сессии есть **явный** override песочницы, он копируется в новую сессию (`session.append('sandbox/mode', …)`) — тем же приёмом, что и driver-агенты в `dsh-task-scheduler`. Без override новая сессия получает деплоймент-дефолт.

## Модель новой сессии

`SessionCreateRequest` модели не принимает вообще: новый чат всегда стартует на `agentDefaultModel.currentSelection()` (`settings.yaml` → `agent-default-model`, иначе строка композиции). Поэтому выбор модели для ребёнка делается после создания, но **не** через `sessionController.selectModel`: тот, кроме сессии, переписывает и дефолт деплоймента (`saveSelection` → `settings.yaml`), то есть следующий чат пользователя поехал бы на модели, которую агент выбрал для исполнителя.

Вместо этого плагин пишет в сессию тот же durable-событие, что и `selectModel`, минуя settings-write:

```js
session.append('model/selection', { provider, model, reasoningEffort? })
```

Проекция `modelSelection` складывает его в `pending`, контроллер читает это как выбранную модель, а `installModelSelection` применяет её в waterfall `agent/request`. Именно поэтому `agentOptions` при создании агента модель **не** фиксирует: установленный селектор перебивает конфиг агента, а без события он падает на деплоймент-дефолт. Событие durable — резюм сессии сохраняет свою модель (`lastUsed`).

Резолвинг параметров: `provider` + `model`; либо `model` в форме `provider/model`; либо голый `model`, если он однозначно находится в каталоге (`sessionController.modelCatalog()`). Маршрут валидируется через `llm.resolveCallConfig`, поэтому отказ адаптера (неизвестная модель, несуществующее усилие) возвращается как ошибка **до** создания сессии — полупустых чатов не остаётся. Без `llm` в деплойменте параметры принимаются как есть.

## Скилл политики делегирования

Инструменты бесполезны, если агент по привычке зовёт `subagent`. Поэтому рядом с инструментами едет инструкция: `skills/managed-sessions/SKILL.md` регистрируется строкой в runtime-слой реестра скиллов (`ctx.skills.register`) — то есть в каталоге скиллов каждой сессии профиля появляется `managed-sessions`, а его тело агент подгружает по триггеру, не тратя контекст заранее. Текст скилла — на английском, как у shipped-скиллов; README и описания инструментов остаются русскими.

Что внутри:

- **маршрутизация**: `subagent` — когда результат нужен в этом же ходу; `session_spawn` — когда работа длиннее хода, должна быть видна пользователю, идёт параллельно или должна пережить сессию;
- **дисциплина**: самодостаточный `prompt`, обязательный `title`, запрет на опрос в цикле (статус — следующим шагом через `session_status`), предел 2–3 живых исполнителя на задачу, разбор `last turn end`, поведение при approval, закрытие ненужных сессий через `session_cancel`;
- **антипаттерны** и требования к отчёту пользователю.

Переопределение: одноимённый скилл в проекте (`<projectRoot>/.dsh/skills/managed-sessions/SKILL.md`) или в `$DSH_HOME/skills/` имеет приоритет над runtime-записью — так политику можно ужесточить в конкретном проекте, не трогая плагин. Формат тот же: YAML-frontmatter с однострочными `name` / `description` / `whenToUse` и Markdown-тело.

Грабли runtime-регистрации, на которые плагин уже наступил: `ctx.skills.register()` сам подставляет `invocation` и `provider`, а вот **`source` не подставляет**. Без него `validateRuntimeSkill` пропускает регистрацию (он проверяет только имя, описание и invocation), каталог скилл показывает — но любая загрузка (`/имя` в поле ввода или модельный инструмент `skill`) идёт через `validateDefinition` и падает с `loaded skill "…" source must be a string`. Поэтому в регистрации явно стоит `source: 'runtime'`, а в `activation.test.mjs` есть проверка на **настоящем** `SkillRegistry`: скилл не просто виден в каталоге, но и загружается.

Проверка после перезапуска: `managed-sessions` появляется в каталоге скиллов сессии; `skill` с этим именем отдаёт полный текст.

## Конфиг

```yaml
- insert:
  - id: dsh-managed-sessions
    name: "dsh-managed-sessions"
    config:
      allowedRoots: []      # пусто = без ограничений
      inheritSandbox: true
      inheritPreset: true   # ребёнок работает под пресетом родителя
      registerSkill: true   # выключить, если политику раздаёт проект/пресет
```

- `allowedRoots` — список каталогов, внутри которых разрешено создавать сессии (`session_spawn` с чужим `cwd` отклоняется) и которыми разрешено управлять через `session_send` (сессия вне корней не примет сообщение). Сравнение — по resolved-путям, поэтому `/a/bc` не проходит для корня `/a/b`. Пустой список полностью снимает фенс: `create` умеет `mkdir -p`, так что без него агент может завести сессию в любом каталоге.
- `inheritSandbox` — наследовать режим песочницы вызывающей сессии при явном override. `false` — всегда деплоймент-дефолт.
- `inheritPreset` — наследовать агент-пресет вызывающей сессии. `false` — все дети на деплоймент-дефолтном пресете.

## Установка

```bash
dsh plugin --profile web add dsh-managed-sessions
# затем один перезапуск dsh web — строки композиции читаются при старте профиля
```

Проверка после перезапуска: в списке инструментов агента появляются `session_spawn` / `session_send` / `session_status` / `session_cancel`, в каталоге скиллов сессии — `managed-sessions`, а в логе хоста две строки: `[managed-sessions] skill "managed-sessions" registered (…)` и `[managed-sessions] host row ready …` с текущим фенсом.

## Тест

```bash
cd dsh-managed-sessions && node activation.test.mjs
```

Изолированный тест активации (38 проверок): монтирует host-половину на стабах сервисов (`tools`, `skills`, `sessionController`, `sessions`, `agents`, `workspaceRegistry`, `sandboxPolicy`) и проверяет регистрацию четырёх тулов и скилла политики (имя и описание из frontmatter, срезанный frontmatter, непустое тело), деградацию без реестра скиллов, `registerSkill: false`, create+prompt, фенс `allowedRoots`, разбор tail в `session_status`, наследование sandbox-режима, `cancel` и чистый `dispose` (включая снятие скилла). Живой DSH не трогает. Нужен резолвящийся `@deepseek-ai/cordis` (в репозитории `node_modules/` в `.gitignore`).

## Ограничения

- **Скилл появляется только после перезапуска** профиля: строка композиции читается при старте. Инструменты и скилл живут одной строкой — `cordis_stop`/выгрузка снимает и то, и другое.
- **Результат не приходит родителю сам.** Subagent-инфраструктура managed-сессию ребёнком не считает, поэтому уведомлений нет: следить нужно через `session_status` (или доработать вотчер: на `turn/end` дочерней сессии доливать follow-up родителю; пока это обязанность агента, и она записана в скилл).
- **Tail читается через `inspect`**, то есть отдаёт весь лог сессии. Для очень длинных логов стоит перейти на `sessionController.page` / `follow` с `maxMessages`.
- **Модель** — деплоймент-дефолт (`agentDefaultModel.currentSelection()`); переключение — `sessionController.selectModel`, в инструменты пока не выведено.
- **Approvals и стоимость** — у новой сессии свои: если она упрётся в эскалацию, вопрос придёт в GUI, а не родителю.
