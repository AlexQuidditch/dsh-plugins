# dsh-peak-hours

Плагин DSH Web: **пиковые часы провайдеров LLM** — по модели сессии, с настоящей
паузой работы и автоматическим возобновлением, рабочим переключателем «разрешить
work in peak hours», кнопкой «отложить до конца пика» в инпуте и UI-обвязкой
(баннер, маркеры в списке сессий, настройки, подсказка модели).

Одна точка правды: расписание хранится в конфиге плагина (и переопределяется из
настроек), а его одновременно используют индикатор, `agent/pre-step`-пауза,
`llm/stream`-гейт, отложенные задачи, контекст системного промпта и инструмент
`peak_hours_status`.

## Что делает

### 1. Пиковые часы по модели сессии
Расписание матчится по `provider` **и** `model` из реального шага сессии
(`agent/pre-step` → `payload.modelSelection`, а для UI — модель из живого агента /
проекции `modelSelection` / дефолта). Ключ — семейство провайдеров
(`deepseek` покрывает `deepseek-account`, `deepseek-official`, `deepseek-vision`;
`zai` — маршруты GLM). У записи может быть `models: { '<model-id>' | '*': {...} }`
для переопределения окон/режима/скидки конкретной модели.

Пилюля в шапке сессии показывает статус **только для модели этой сессии**:
«пик через 12 мин», «конец пика через 1 ч 20 мин», «на паузе до 10:00»,
«пик · разрешено», «пик: окна не заданы». В поповере имя модели берётся из
каталога провайдера (`DeepSeek-V4.1-Flash`), а если в списке окон оказывается
несколько провайдеров, каждая строка подписана семейством — два разных
провайдера могут пиковать в один и тот же локальный час (DeepSeek 06:00–10:00 UTC
и GLM 14:00–18:00 по Пекину — это одни и те же 08:00–12:00 в Йоханнесбурге).

### 2. Пауза на пик и авто-возобновление
`mode: pause` (по умолчанию) — плагин вешает waterfall-слушатель
`agent/pre-step` (root, prepend) и в пиковое окно, если работа в пик запрещена:

- **HOLD** (короткое окно или середина задачи) — ждёт конца окна прямо между
  шагами; turn остаётся открытым, модель не вызывается, деньги не тратятся;
  по завершении окна шаг продолжается сам, без внешнего «будильника».
- **REQUEUE** (долгое окно, активная goal-сессия) — промпты, уже заклеймленные
  из inbox, сохраняются в durable-очередь `$DSH_HOME/peak-hours.json`, turn
  закрывается `blocked`, сессия становится idle; на конце окна сообщения
  доставляются обратно через `agent.send(... 'next-turn', true)`, в том числе
  после рестарта хоста.
- Цепочка `auto` выбирает HOLD для коротких окон (≤ `pause.maxHoldMinutes`) и
  REQUEUE для длинных. Subagent-сессии всегда HOLD (их нельзя переактивировать).
- Перед паузой делается durability-checkpoint (`sessions.flush`).
- If the user presses Stop (abort) during a hold — claimed prompts are restored
  to the inbox, nothing is lost.

### 2a. Субагенты и команды

Пауза распространяется и на субагентов: плагин слушает `agent/pre-step` на
корневом контексте, а scoped-события DSH всплывают от дочерних scope к
родительскому, поэтому каждый шаг дочерней сессии гейтится отдельно (и
`llm/stream`-гейт видит её вызовы тоже). Особенности:

- дочерняя сессия **никогда не уходит в requeue** — только `hold`: после
  `reject` child нельзя безопасно переактивировать (в отличие от обычной сессии);
- **allow наследуется от ближайшего предка**: включил «Разрешить работу в peak
  hours» у родителя — субагенты работают; снял — они встанут на следующем шаге;
  собственный override дочерней сессии всегда важнее унаследованного;
- «Продолжить сейчас» у родителя освобождает удерживаемые шаги всего дерева;
- дневной бюджет пикового времени общий для всех сессий;
- пик считается по модели каждого шага: если субагенту явно назначена другая
  модель/провайдер, у него может быть другое окно;
- у субагентских сессий UI плагина (пилюля, баннер, кнопка «отложить») скрыт:
  откладывать задачи на child-сессию штатный `schedule` не умеет;
- тимейты Agent Teams — самостоятельные верхнеуровневые сессии: наследуют только
  глобальный дефолт, если у них нет `parentSession`.

Ограничение: уже выполняющийся tool call не прерывается. Если родитель ждёт
субагента, а тот в пике и работа в пик ему не разрешена, родитель дождётся конца
окна (или «Продолжить сейчас» у родителя).

### 3. Переключатель «Разрешить работу в peak hours»
По умолчанию `false`. Работает в двух областях: чекбокс в поповере пилюли —
для **текущей сессии** (ключ sessionId в state-файле), глобальный дефолт — в
настройках/конфиге. Пока флаг выключен и идёт пик — сессия паузится (пункт 2);
пока включён — вызовы идут, а израсходованное пиковое время учитывается в
дневном бюджете.

- `resume-now` — «Продолжить сейчас» (временно, до конца пика/на N минут/навсегда).
- `pause-now` — вернуть запрет.
- `dailyLimitMinutes` — дневной лимит пикового времени; после исчерпания
  переключатель перестаёт действовать до следующего дня (защита от «забыл
  выключить»).

### 4. «Отложить до конца пика»
- **Кнопка в инпуте** (`conversation.input.right`): `⏰ до HH:MM` появляется в
  пик для модели сессии; берёт текущий черновик, создаёт one-shot задачу в
  штатном `schedule`-сервисе DSH на момент «конец пика + margin», очищает
  черновик. Задача durable, видна в Automation UI, переживает рестарт, умеет
  поднимать закрытую сессию; вложения не переносятся (кнопка блокируется).
- **Баннер в композере** (`conversation.input.dock`): «пик до 10:00 — пауза»,
  «скоро пик», «пик разрешён», «бюджет исчерпан» + действия.
- `cancel-defer` отменяет и запланированные задачи, и очередь сообщений паузы.

## Дополнительные возможности

- **Баннер в композере** с действиями «Продолжить сейчас» / «Отложить черновик» /
  «На паузу».
- **Маркер в списке сессий** (`sidebar.session.row.trailing`): `⏸` пауза, `⏰`
  отложенные сообщения.
- **Предупреждение перед пиком** (`prePeakWarningMinutes`, по умолчанию 10 мин):
  янтарная пилюля и баннер «пик через N мин»; при скрытой вкладке — browser
  notification, если разрешение уже выдано.
- **Контекст для модели + инструмент** `peak_hours_status`: системный контекст
  сообщает текущий режим/окно/бюджет, инструмент отдаёт JSON-статус; модель
  может сама отложить дорогую работу на непиковые часы.
- **Оценка экономии**: `savedTokensEstimate ≈ movedTokens × offPeakDiscount`,
  плюс реальные `peakCalls`/`peakTokens`/`pausedSeconds`/`heldSteps`/`deferredMessages`.
- **Предпиковый чекпоинт**: `sessions.flush` перед паузой.
- **Пик-aware goals**: активная goal-сессия не висит в `running` часами — для неё
  выбирается REQUEUE.
- **Маркеры в транскрипте** (`conversation.chat.turnTail`): `🌙 пик` —
  turn выполнялся в пиковые часы, `⏸ был на паузе в пик`.
- **Страница настроек** (Настройки → «Пиковые часы»): режим, лимиты, пороги,
  background-политика и визуальный редактор расписаний (окна, таймзоны, дни
  недели, модельные переопределения), сброс к встроенным.

Осознанно **не** делались: автопереключение модели на непиковый провайдер и
«дешёвые модели не паузить» — оставлены как идеи на будущее.

С `dsh-task-scheduler` не конфликтуем и не дублируем его: отложенная отправка
идёт через штатный `schedule`-сервис DSH (Automation UI), а task-scheduler
остаётся планировщиком скриптов/cron-задач.

## Конфиг

Бандл-патч (`cordis.patch.yml`) — дефолты; страница настроек пишет
пользовательские переопределения в state-файл.

```yaml
config:
  enabled: true
  mode: pause                 # pause | hard | warn
  pause:
    strategy: auto            # auto | hold | requeue
    maxHoldMinutes: 20
    checkpoint: true
  allowPeak: false            # глобальный дефолт «разрешить пик»
  dailyLimitMinutes: null     # null = без лимита (текущий дефолт)
  prePeakWarningMinutes: 10
  backgroundPolicy: allow     # session-title / compaction / auto-review: allow|warn|block
  schedules:
    deepseek:                 # семейство: deepseek / deepseek-account / deepseek-official / deepseek-vision
      windows:
        - { start: "01:00", end: "04:00", tz: "UTC", days: [1, 2, 3, 4, 5] }
        - { start: "06:00", end: "10:00", tz: "UTC", days: [1, 2, 3, 4, 5] }
      # models: { deepseek-reasoner: { windows: [...] } }   # опционально
    zai:                      # GLM Coding Plan, пн–пт 14:00–18:00 по Пекину
      windows:
        - { start: "14:00", end: "18:00", tz: "Asia/Shanghai", days: [1, 2, 3, 4, 5] }
      offPeakDiscount: 0.5
```

`days` — 0=вс..6=сб; уберите ключ, чтобы окно действовало каждый день. Окна могут
пересекать полночь; для «круглосуточно» используйте `00:00`–`23:59` (окно нулевой
длины `00:00`–`00:00` отклоняется как битое). Запись расписания может нести свой
`mode`/`offPeakDiscount` и `models: { <model-id>|'*': {...} }` — они переопределяют
семейство для конкретной модели. Битое окно и неизвестный провайдер — fail-open
(warn, никогда не блок). `offPeakDiscount` (0..1) используется только для оценки
экономии.

### Праздники Китая (исключения из пика)

Официальный текст цен: пиковые часы — пн–пт **кроме китайских государственных
праздников**; в праздники и выходные действует непиковый тариф. Плагин умеет это
учитывать: у записи расписания есть необязательный календарь исключений

```yaml
    deepseek:
      windows: [ ... ]
      holidays:
        tz: "Asia/Shanghai"      # праздники объявлены по Китаю
        ranges:                  # включительные диапазоны YYYY-MM-DD
          - ["2026-10-01", "2026-10-07"]
```

На датах из диапазонов пиковые окна не действуют вообще (движок не считает это
пиком, пауза не включается, `peak_hours_status` и пилюля показывают «не пик»).
В бандле уже лежит официальный календарь КНР на 2026 год
(国办发明电〔2025〕7号: 元旦, 春节, 清明节, 劳动节, 端午节, 中秋节, 国庆节).
Даты проверяются в таймзоне `tz`, битые даты/диапазоны отбрасываются с warn.
Раз в год список удобно обновлять в Настройки → «Пиковые часы» → карточка
провайдера → «Праздники-исключения» (строки `YYYY-MM-DD` или
`YYYY-MM-DD..YYYY-MM-DD`).

## Откуда взяты окна

**DeepSeek** — страница цен: 01:00–04:00 и 06:00–10:00 UTC, пн–пт.

**GLM Coding Plan** (Z.ai / 智谱) — [docs.bigmodel.cn/cn/coding-plan/overview](https://docs.bigmodel.cn/cn/coding-plan/overview),
раздел «积分抵扣计算方式»: 高峰 — пн–пт 14:00–18:00 по Пекину (= 06:00–10:00 UTC),
непиковые вызовы списывают 50% базовых кредитов. Окно объявлено в
`Asia/Shanghai`, поэтому день недели считается по Пекину.

## Архитектура

| файл | роль |
|---|---|
| `lib/schedule.js` | чистый движок: окна, TZ/DST, дни, модельные переопределения, `overviewFor`, `peakEndsAt`, `nextPeakStartAt` |
| `lib/state.js` | durable state `$DSH_HOME/peak-hours.json`: overrides, настройки, расписания, stats, дневной лимит, очередь, маркеры turns; миграция легаси-файла |
| `lib/config.js` | слияние конфига бандла и пользовательских настроек; `allowFor()` |
| `lib/stats.js` | счётчики экономии, дневной бюджет, rolling-оценка токенов/шаг |
| `lib/pause.js` | `agent/pre-step` пауза: hold/requeue, восстановление claimed, доставка очереди, checkpoint |
| `lib/gate.js` | `llm/stream` гейт: `hard`-блокировка, background-политика, учёт пиковых вызовов |
| `lib/defer.js` | one-shot `schedule`-задачи на конец пика + re-arm при загрузке |
| `lib/context.js` | секция системного контекста + инструмент `peak_hours_status` |
| `lib/index.js` | wiring, RPC-канал `/dsh-peak-hours`, сборка snapshot |
| `lib/client.js` | вся Web-половина: пилюля, поповер, кнопка, баннер, маркеры, настройки |

Host-модули не импортируют `@deepseek-ai/*` (linked-плагин их не резолвит) —
только `node:*`, локальные файлы и сервисы через `ctx.get()`/`ctx.inject()`.
Контракт RPC и snapshot зафиксирован в [CONTRACT.md](CONTRACT.md).

Сервисы DSH, которые используются: `connection` (RPC), `agents`, `sessions`,
`sessionProjections`, `agentDefaultModel`, `sessionController` (для подъёма
закрытых сессий), `schedule` (опционально), `systemPrompt`, `tools`, `goals`.
При отсутствии опционального сервиса плагин деградирует, а не падает.

```bash
dsh plugin --profile web add ~/projects/dsh-plugins/dsh-peak-hours
# host-половина (pause, gate, defer, tool, RPC) грузится при старте процесса,
# поэтому нужен перезапуск dsh web; клиентская половина обновляется перезагрузкой

```

## Если пилюля пишет «хост не перезапущен»

Это значит, что страница уже загрузила новую клиентскую половину, а процесс
`dsh web` всё ещё работает со старой хост-половиной. В таком состоянии хост не
отдаёт модель сессии, бюджет, паузу и статистику — UI показывал бы
правдоподобные, но неверные «без лимита», «—» и «пик не в ближайшее время».
Предупреждение сделано компактным и не действует на нервы: строка с иконкой,
коротким заголовком и одной подсказкой, кнопка «Что сделать?» раскрывает шаги
(перезапустить процесс, обновить страницу), кнопка «Скрыть» убирает баннер до
перезагрузки страницы — в шапке сессии остаётся индикатор «хост не перезапущен».
Перезапустите `dsh web` (один раз), после рестарта всё встанет на место: пилюля
покажет «пик через N мин», поповер — бюджет `0 / 30 мин` и окна только твоей
модели. Клиентские правки подхватываются обычной перезагрузкой страницы,
хост-правки — только рестартом процесса.

## Ограничения

- Пауза работает на границах шагов: уже начатый вызов модели/инструмента не
  прерывается (это осознанно).
- В отложенное через `schedule` сообщение нельзя перенести вложения/чипы
  ссылок — только текст; доставка приходит модели как scheduled-reminder.
- В `hard`-режиме блокировка вызова неретраябельна (обычно используйте `pause`).
- Календарь праздников статичен (годовые даты в конфиге/настройках) — обновляйте
  его раз в год; сам плагин не тянет праздники из сети.
- Два провайдера могут иметь одинаковое локальное время окон; в поповере такие
  строки подписываются семейством, но на глаз в другом часовом поясе это всё
  равно легко спутать.
- Host-половина обновляется только со стартом `dsh web`; план за паузу переживает
  рестарт, активная открытая turn-пауза (hold) — нет (после рестарта сообщение
  останется в очереди только при requeue-стратегии).
- Ключи слотов, проекция `modelSelection`, `schedule/*` — внутренние контракты
  DSH 0.2.2-rc.1; для сторонних плагинов semver не гарантируется.

## Диагностика

- Поповер пилюли: модель сессии, статус, режим, бюджет, окна, статистика.
- Хост-лог: `[peak-hours] ...` (пауза, доставка, блокировки, ошибки re-arm).
- `peak_hours_status` — тот же статус из модели.
