# dsh-scope-router

Host-плагин DeepSeek Harness: **автоматическое внедрение инструкций проекта по скоупу работы агента**.

Определяет, над чем работает агент — в каком проекте (`projectRoots`), в каком доменном
пакете (`packages/domains/<name>`) и на каком слое (backend/frontend) — по трём сигналам:

1. текст сообщения (упоминание домена / ключевые слова слоя);
2. файловая активность (`fs/observed`);
3. shell-активность (`tools/result` для `bash`/`pwsh`: `workdir` и пути в `command`).

При смене скоупа перед шагом модели внедряется бандл инструкций: ядро (`coreFiles`) +
доменный файл (`domainCandidates`) + послойные карты (`layerFiles`). Новая подборка
текстуально заменяет предыдущую. Вне проекта роутер бездействует.

## Workspace-гейтинг (с v0.2.0)

Роутер учитывает **workspace сессии агента** (`agent.session.header.cwd`):

- root из `projectRoots` элиджиблен для агента только если его cwd равен root'у или
  лежит внутри него. Агент, работающий в другом репозитории, **не получает никаких
  инструкций**, даже если текст диалога упоминает домены проекта (постмортем:
  инструкции `platform` утекали агентам в чужих репо через упоминания и активность);
- вся файловая и shell-активность атрибутируется **конкретному агенту**
  (`ToolExecution.agent`; `actor` события `fs/observed` несёт того же агента) и
  хранится в пер-агентских картах — в многосессионном `dsh web` активность одного
  агента не повышает скоринг root'а для другого;
- относительные фрагменты путей (`packages/...`, `apps/...`) из shell-команд
  резолвятся только против root'ов, содержащих cwd **действующего** агента:
  команды из чужого репозитория больше не фабрикуют пути внутри сконфигурированных
  root'ов;
- заголовок бандла называет рабочий workspace и root проекта; пробный тул
  `scope_router_status` показывает состояние гейтинга и недавнюю активность
  с атрибуцией по агентам.

Чтобы покрыть другой репозиторий — добавьте его корень в `projectRoots` с его собственными
`coreFiles`/`layerFiles`: роутер мульти-root'овый, каждый root обслуживает агентов
своего workspace.

## Worktree-пиннинг (с v0.3.0)

Сессия, созданная внутри каталога worktree'ов (`worktrees.dir`, например
`~/projects/platform.worktrees`), получает скоуп **по имени worktree-каталога**:

- root для чтения файлов — сам worktree, т.е. инструкции берутся из чекаута
  соответствующей ветки, а не из основного репозитория;
- домен закреплён именем каталога (`worktrees.domainByWorktree` переопределяет
  соответствие «имя → домен», по умолчанию они совпадают): ни текст диалога, ни
  файловая/shell-активность не могут переключить домен или подтянуть файлы
  другого домена — например, диалог в `obnime` получает только obnime;
- `worktrees.includeCore` (по умолчанию `true`) добавляет корневые `coreFiles`
  worktree — без них worktree без доменного файла (сейчас это `obnime`,
  `pilot-school`, `monitor-sts`) не получал бы ничего, кроме правил репо;
- `worktrees.includeLayers` (по умолчанию `false`) добавляет послойные карты;
- относительные `packages/…`/`apps/…` из shell-команд агента worktree
  резолвятся против корня его worktree;
- заголовок бандла называет пиннинг; пробный тул `scope_router_status` показывает
  каталог worktree'ов и `pinned=yes/no` в последней детекции.

### Все файлы скоупа + fallback на основной root (v0.4.0)

В pinned-режиме инжектятся **все найденные** файлы скоупа из `domainCandidates`
(например, одновременно `packages/domains/<app>/AGENTS.md` и `apps/<app>/AGENTS.md` —
это дополняющие файлы, а не приоритетная цепочка; в угаданном режиме main-root
поведение прежнее — первый найденный).

Если ветка worktree ещё не содержит какой-то файл скоупа (его добавили в основной
репозиторий, но не слинковали в worktree), файл читается **из основного root**
(`projectRoots`), а заголовок бандла и лог отмечают это. После `worktree-app.sh
sync` (merge develop) файл начинает читаться из чекаута worktree.

Новый worktree подхватывается без правки конфига: создали `worktree-app.sh
ensure <app>` + workspace — плагин сам пиннит скоуп по имени каталога.

## Сборка

```bash
pnpm install
pnpm run build        # tsc → lib/
node activation.test.mjs
```

## Установка в профиль

```bash
dsh plugin --profile web add ~/projects/dsh-plugins/scope-router
dsh --dump-config --profile web   # строка scope-router в дереве
# перезапустить dsh web
```

## Конфиг (в cordis.patch.yml пакета)

| Ключ | Описание |
| --- | --- |
| `projectRoots` | абсолютные корни проектов; без них плагин неактивен |
| `coreFiles` | root-относительные файлы ядра (всегда) |
| `layerFiles` | `{ backend: [], frontend: [] }` — послойные карты |
| `domainsDir` | каталог, поддиректории которого = домены |
| `domainCandidates` | шаблоны доменных файлов, `{domain}` заменяется именем |
| `maxBundleChars` | кап одного бандла (по умолчанию 80000) |
| `probeTool` | регистрировать отладочный тул `scope_router_status` |
| `log` | логировать инъекции |
| `worktrees.dir` | каталог worktree'ов: сессия внутри `<dir>/<name>` пиннится к скоупу `<name>` |
| `worktrees.domainByWorktree` | переопределение «имя каталога worktree → домен» |
| `worktrees.includeCore` | core-файлы в worktree-бандле (по умолчанию `true`) |
| `worktrees.includeLayers` | послойные карты в worktree-бандле (по умолчанию `false`) |
